#2018: Classifier: brace groups after then/do/else/!/time (and } after fi/done/esac) are read as literal in #2005's new reading

Follow-up from #2005 by @ryssroad (thank you!), found by the independent round-2 security review. Not a security regression: every case below is still judged with main's reading as well, so the result is never quieter than before #2005.

**What:** #2005's new reading treats `{` / `}` as group delimiters only in command-word position, detected as `current.words.is_empty()` (`codex-rs/core/src/security/tainted_action/shell.rs`, the `{`/`}` arms of the lexer). That check does not recognise real brace groups that open right after a reserved word or close right after a compound-command terminator:

- `if true; then { echo g; }; fi` — `{` after `then`
- `for x in a; do { echo d; }; done` — after `do`
- `if false; then :; else { echo e; }; fi` — after `else`
- `! { echo n; }` — after `!`
- `time { echo t; }` — after `time`
- `{ if true; then echo in; fi }` — `}` right after `fi` (also `done`, `esac`) with no `;`

All of these run as groups in bash. The new reading keeps those braces literal, so it can glue the group's first command onto the keyword (e.g. `then {`). It always sets `read_newly`, so main's reading still decides.

**Suggested fix:** also treat the brace as a group delimiter when the current command's words so far are only reserved words (`then`, `do`, `else`, `elif`, `!`, `time`, …), and accept `}` after `fi`/`done`/`esac`. Add tests for each spelling above, in bash and zsh, plus a never-quieter check against the current main.
