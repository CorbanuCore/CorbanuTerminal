I've fixed #2046 and committed it locally in two commits. The bug was real: a turn being stopped in guardian's background wait took the new turn's input.

**What was wrong:** When guardian stops a turn after too many denials, it does it in the background. It first clears the active-turn slot, then waits up to 100 ms for the old task to finish. If the user starts a new turn in that window, the new turn takes the slot. The old turn's next input check (in `run_turn`) then read whatever turn was in the slot. So it took the new turn's steered message and its agent messages.

**Fix (`codex-rs/core/src/session/`):**
- **`input_queue.rs`:** `get_pending_input_for_running_task` now also takes the polling turn's `sub_id`. It only takes input when the active slot's task belongs to that same turn; otherwise it returns nothing and leaves the input where it is. Guardian's targeted stop and `turn_state_for_sub_id` already identify turns by `sub_id`. The task-start path and the test-only `get_pending_input` behave as before.
- **`turn.rs`:** `run_turn` passes `&turn_context.sub_id` when it checks for input.
- **`stale_poll_mail_tests.rs`:** new regression test `guardian_stopping_turn_does_not_take_the_next_turns_input`. It runs guardian's stop in a detached task, as guardian does. While the old turn is still stopping, it starts a new user turn, steers a message into it and queues an agent message. Then the old turn checks for input. The test expects the old turn to get nothing and the new turn to still hold both items. The old turn's check runs in a detached helper task, so the result doesn't depend on beating the 100 ms timer.
- **Release note:** `qa/release/unreleased/notes/2046-stopping-turn-leaves-next-turn-input.md`, under the existing `## Agents and reviews` heading. `release_notes.py check` passes.

**Not done or unsure:**

- **Relies on unique turn ids:** the fix assumes each turn has its own `sub_id`, which guardian's stop already assumes.
