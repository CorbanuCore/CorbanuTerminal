The bug is real and now fixed. Guardian stops a turn in the background and waits up to 100 ms for it to finish. A turn the user starts in that window could have its steering input and queued agent messages taken by the turn being stopped. Now the stopping turn only takes its own input. The regression test fails before the fix and passes after, the focused tests pass, and clippy and fmt are clean on the pinned toolchain.

**Cause:** `run_turn` polled whatever turn was currently active, without checking whose it was. Once guardian's stop had removed the old turn, a new user turn could take its place. The stopping turn's next poll then took the new turn's steer and mail, and the new turn lost them.

**Fix** (in `codex-rs/core/src/session/`):
- **`input_queue.rs`:** `get_pending_input_for_running_task` now takes the calling turn's id. If the active turn belongs to a different task, or its task isn't installed yet, it returns nothing and touches neither that turn's input nor the mailbox. Turn startup and the test-only helper behave as before.
- **`turn.rs`:** `run_turn` passes its own turn id (`turn_context.sub_id`). A task is always installed before it can poll, so a running turn still gets its own input.
- **`stale_poll_mail_tests.rs`:** adds the regression test `guardian_stopping_turn_does_not_take_the_new_turns_input`. Existing callers now pass a turn id.
- **Release note:** added `qa/release/unreleased/notes/2046-stopping-turn-leaves-new-turn-input.md`, reusing the heading from the #2033 note. `release_notes.py check` passes.

**The test** follows the #1999/#2033 style. It starts a turn, runs guardian's stop in a detached task, and waits (bounded) for the old turn to be removed. It then starts a new turn, steers it and queues a trigger agent message. Finally it lets the stopping turn poll inside the 100 ms window. It checks that the stopping turn got nothing and the new turn still has both items.

**Unsure or not done:**
- The test depends on the stopping turn polling inside the real 100 ms window. If the machine were slow enough to miss it, the test would fail (the turn never polls); it would not falsely pass.
- `has_pending_input` (used by the regular-task loop) still checks the active turn without a turn id. A stopping turn could see the new turn's input there and loop once more. It can no longer take that input, and its cancellation stops it, so I left this alone to keep the change scoped.
- There's no live interactive (TUI) test; the evidence is the unit and integration tests above.
