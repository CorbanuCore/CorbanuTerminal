## Security

Command rules now read literal quoted words in shell scripts (#2543, D553, D688): `bash -lc "'git' push"`, `"git" push`, `g'i't push`, `'/usr/bin/git' push` and `echo hi; 'git' push` are checked like `bash -lc 'git push'`. Scripts that are more than plain commands (redirections, substitutions, loops, functions) are now read for prompt and forbidden rules too, as are `dash -c` and `ksh -c` scripts. Where a command is only known once the script runs (`$cmd push`, `"$(echo git)" push`, `/usr/bin/gi? push`), or a shell gets a script rules cannot read (`bash -c '…' name`, `fish -c '…'`), the command asks for approval whenever a prompt or forbidden rule could match it; with no such rule, nothing changes. Allow rules still never approve a script through this partial reading. Run-time launcher words such as `env X="$PWD/y" cmd` can also require approval; with approvals disabled, commands that need approval are refused. This is not complete shell interpretation: code supplied through `eval`, shell stdin, here-documents or sourced files remains a follow-up (#2548), as does a POSIX script passing a run-time word to PowerShell (#2585). See [command rules](https://github.com/CorbanuCore/CorbanuTerminal/blob/sync/upstream-rust-v0.167.0/docs/execpolicy.md) for examples and limits.

On macOS and Windows, the built-in dangerous-command check now matches program names in any case (`RM -rf x`, `/bin/Rm -f x`, `SUDO rm -rf x`), as those systems run them (D692); the safe-command list is unchanged.
