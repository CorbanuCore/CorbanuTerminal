## Security

On Windows, `allow` command rules (including remembered "always allow" rules) now approve only the program name exactly as the rule spells it, as on macOS and Linux (D696, #2553). Before, Windows read a command's program by its lower-cased name without `.exe`, `.cmd`, `.bat` or `.com`, so an `allow` rule for `rm` or `git push` also approved `RM x`, `GIT.EXE push` or `C:\Program Files\Git\cmd\git.exe push`. Those spellings no longer receive approval from that allow rule; the remaining rules and safety checks decide whether to ask. When no `host_executable` lists the program, a path whose file name is spelled as in the rule (`C:\tools\git push` for `git`) is still allowed. When one does, only the listed paths are allowed, spelled exactly as listed, drive letter case included. Listing a path is a way to approve `git.exe` by path without a prompt, but note that a listing also stops `forbidden` and `prompt` rules for that name from applying to paths outside the list. `forbidden` and `prompt` rules still match the same Windows spellings as before. On sync, a rule explicitly using `canonical_matching=True` still opts into case-insensitive token comparison; listed allow paths still require their recorded spelling. Existing rules files load unchanged, including their `match` and `not_match` examples; only which commands `allow` rules approve without asking has narrowed.
