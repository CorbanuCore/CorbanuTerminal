## Windows sandbox

- Commands run through `cmd.exe /C` in the Windows sandbox (both backends, with or without a terminal) now reach cmd exactly as written, so quoted paths such as `echo hi > "%TEMP%\out.txt"` work. Previously the sandbox quoted them for ordinary programs, which cmd misreads: such commands failed, and a quote inside an argument could make cmd run text after it as a separate command. cmd now starts with `/D /S /V:OFF` (no registry AutoRun commands, delayed `!VAR!` expansion off unless the caller chose `/V`). A program given with separate arguments after `/C` receives each argument unchanged, with no `%VAR%` expansion or operators; arguments cmd can't pass on unchanged (line breaks, NUL, `/V:ON`, `CALL` as the program) are refused instead of run. A batch file (`.bat`/`.cmd`, started directly or named after `/C`) is refused when an argument contains a character cmd acts on (`" % ! ^ & | < > ( )`); started directly, its own path may not contain them either (so a batch file under `Program Files (x86)` must be run through `cmd /c`). A bare name cmd finds through PATHEXT (for example `npm` for `npm.cmd`) isn't recognized as a batch file. A script path given alone after `/C` is now read as typed, so a path with spaces must be quoted (#2702, D730).
