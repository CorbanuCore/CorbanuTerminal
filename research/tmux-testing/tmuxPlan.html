Governance position

This is internal test infrastructure that cannot itself change user-visible behavior, authorization, persistent state, or an external contract. It therefore fits the repository's Routine change class. Calling the work a sprint is useful for execution discipline, but it should not consume a governed product-plan slot unless product scope is added. Product-specific scenarios should be owned by the feature sprint that depends on the harness.

Testing Architecture

Use the cheapest layer capable of observing the failure. tmux complements the existing layers; it does not replace them.

Layer 1

Ratatui snapshots

Deterministic rendering, component states, wrapping, and visual regressions.

Layer 2

PTY process tests

Process startup, raw input/output, resize calls, exit, and Windows ConPTY parity.

Layer 3

Typed tmux driver

Live viewport, real key translation, panes, resize/reflow, interruption, and cleanup.

Layer 4

Release matrix

Long product workflows, live repositories, evidence collection, and human acceptance.

Requirements

Functional

  1. Create a unique tmux server, session, and pane at fixed dimensions.
  2. Launch a selected Corbanu candidate with temporary home, workspace, logs, and deterministic mock provider.
  3. Send literal text and named terminal keys through separate, typed methods.
  4. Capture the live viewport separately from bounded scrollback.
  5. Wait for semantic conditions and a stable character grid.
  6. Resize clients, split and close panes, and retain stable pane identities.
  7. Inspect pane process, dimensions, command status, and clean exit.
  8. Emit a complete diagnostic bundle automatically on timeout or failure.
  9. Terminate sessions, servers, and child processes on success, error, and panic.

Non-functional

  1. Parallel-safe isolation using unique tmux sockets and temporary paths.
  2. No live credentials, external network, or live model requirement.
  3. Bounded polling; no unconditional sleeps in the reusable harness.
  4. Errors include the failed command, status, stdout, stderr, and reproduction command.
  5. No retries that conceal nondeterministic behavior.
  6. Linux and macOS tmux support with PTY/ConPTY retained for Windows.
  7. CI smoke runtime target below 30 seconds at the 95th percentile.
  8. Artifact names and metadata remain stable enough for CI collection and comparison.

Proposed API

pub struct TmuxServer { /* unique socket and cleanup guard */ }
pub struct TmuxSession { /* session identity and size history */ }
pub struct TmuxPane { /* immutable pane id */ }

impl TmuxServer {
    pub fn start(spec: ServerSpec) -> Result<Self>;
    pub fn new_session(&self, spec: SessionSpec) -> Result<TmuxSession>;
}

impl TmuxSession {
    pub fn primary_pane(&self) -> &TmuxPane;
    pub fn split(&self, spec: SplitSpec) -> Result<TmuxPane>;
    pub fn resize_client(&self, size: TerminalSize) -> Result<()>;
    pub fn wait_for_exit(&self, timeout: Duration) -> Result<ExitStatus>;
}

impl TmuxPane {
    pub fn send_literal(&self, text: &str) -> Result<()>;
    pub fn send_key(&self, key: TmuxKey) -> Result<()>;
    pub fn capture_viewport(&self, label: &str) -> Result<Screen>;
    pub fn capture_scrollback_tail(&self, lines: usize) -> Result<String>;
    pub fn wait_until(&self, condition: ScreenCondition) -> Result<Screen>;
    pub fn wait_stable(&self, condition: ScreenCondition) -> Result<Screen>;
}

Implementation Sequence

Step 1

Define the harness contract

Add the support module, typed identifiers, session specification, terminal size, key enum, capture type, timeout policy, and command error type. Detect tmux availability and version explicitly.

Step 2

Build isolation and lifecycle

Use a unique tmux -L socket, generated session name, fixed dimensions, temporary CODEX_HOME and workspace, and panic-safe cleanup. The harness must never contact the developer's default tmux server.

Add input, capture, and synchronization

Target immutable pane IDs. Implement literal text and named keys separately. Synchronize against the live viewport and require two identical captures after a semantic condition is met; use scrollback only as diagnostic evidence.

Required Tests

Test Proof Failure evidence
Unique server isolation Two concurrent harness instances cannot list, capture, target, or kill each other's panes. Both socket names, sessions, and pane listings.
Literal versus key input send_literal("Enter") types text; send_key(TmuxKey::Enter) emits the key. Viewport before and after each input.
Stable-grid synchronization A condition passes only after two consecutive identical live viewport captures. Timestamped capture sequence.
Viewport versus scrollback Text present only in stale scrollback cannot satisfy a live-screen wait. Viewport and bounded scrollback shown together.
Resize identity Resize and split operations retain the target pane ID and record every dimension change. Layout and dimension timeline.
Timeout artifacts An impossible condition returns a bounded error and writes every required artifact. The generated artifact manifest.
Crash and panic cleanup Candidate crash and unwinding leave no tmux server, session, or child process. Post-cleanup process and socket checks.
Command diagnostics A failed tmux invocation reports command, status, stdout, stderr, and reproduction syntax. Structured error equality assertion.
Tool availability policy Missing tmux skips clearly for opt-in local tests and hard-fails the dedicated CI lane. Explicit policy message, never a silent pass.
Migrated resize workflow Sentinel content and composer remain anchored across split, resize, restore, and clean exit. Named captures and size history.
Single-Enter slash dispatch Command text and one separate Enter open the expected command surface without fallback input. Input event ledger and resulting viewport.

Program Acceptance Gates

Recommended gate: the focused TUI test suite passes normally; the tmux smoke lane completes 50 consecutive repetitions with no failures, no leaked servers or child processes, and a measured p95 runtime below 30 seconds. The migrated test is no longer ignored in the tmux-equipped lane, and every induced failure produces the documented artifact bundle.

The current package has a smaller exit gate: one migrated resize test, focused and full codex-tui tests, 20 clean repetitions, private-server cleanup, and proof that the developer's default tmux server was untouched. The exact checklist lives in RW-TMUX-01.

Definition of done

  • The support API and its contract tests are reviewed and documented in code.
  • One existing resize test uses the harness instead of direct repeated tmux commands.
  • The historical single-Enter slash-command failure has automated coverage.
  • The Ubuntu CI lane installs tmux, runs the smoke set, and preserves failure artifacts.
  • The existing release matrix remains operational and can begin adopting the harness incrementally.
  • Measured duration, repetition count, flake count, and cleanup check are recorded in the change evidence.

Explicitly out of scope

Do not include in the first increment: a general terminal automation framework, a new workspace crate, full tmux control-mode event parsing, wholesale migration of the release matrix, Windows tmux support, pixel-image comparison, live-provider tests, or every multi-pane orchestration scenario.

Follow-on work

  1. Control mode and multi-pane: parse tmux control notifications for exact output, layout, and pane lifecycle boundaries.
  2. Scenario migration: let the release matrix consume the typed driver or a thin command wrapper while retaining high-level product flows.
  3. Feature qualification: add success, cancellation, recovery, resume, and authorization scenarios as their owning product sprints require them.
